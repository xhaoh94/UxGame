## 模块重命名：Manager/State → Manager/Combat

用户提出把 State 目录改成 Combat，并询问 `CombatController` 是否该改成 `CombatMgr`。

### 项目命名规则（已确认，后续重构通用）
- `HotfixBase/Manager/<模块>/` 下，模块入口统一叫 `<模块名>Mgr.cs`，且都是 `Singleton<T>`：
  ConditionMgr / EvalMgr / EventMgr / FogOfWarMgr / ModuleMgr / NetMgr / TagMgr /
  TimeMgr / TimelineMgr / UIMgr / WayfindingMgr
- **模块入口 .cs 放模块根目录**，不在 Runtime/ 下（TimelineMgr.cs、ConditionMgr.cs 均是）
- `Controller` 后缀 = 实例级（每对象一个），非单例：AsyncController / DoorController /
  TimeoutController / CombatController

### 结论：CombatController 不改成 CombatMgr
它是 per-Unit 实例（`CombatComponent.cs:25` 是 `new CombatController()`，测试里 5 次 new），
`CombatProfileMgr` 的注释原话就是"所有运行时状态都保存在每个 Unit 的 CombatController 中"。
改成 Mgr 违反 Mgr=单例 的隐含契约，且会占用将来真正的模块入口名（管 BattleWorld / 帧调度）。

### 实际改动
| 改动 | 说明 |
|---|---|
| `Manager/State/` → `Manager/Combat/` | 连同 `State.meta` → `Combat.meta`，22 个文件（含 meta） |
| `Hotfix/Common/State/` → `Hotfix/Common/Combat/` | CombatComponent.cs 所在 |
| `Combat/Runtime/CombatProfileMgr.cs` → `Combat/CombatProfileMgr.cs` | 对齐 TimelineMgr 的根目录惯例 |
| 文档路径同步 | COMBAT_DESIGN.md（4 处）+ 本次记忆 |

### 关键校验（通过）
- 所有 .meta 跟随移动，**GUID 未变**，ScriptableObject 资产引用完好
  （HeroZSCombatProfile.asset → guid 441cd290...，HeroZSAttack01.asset → guid 3b752651...）
- 无硬编码路径引用 `Manager/State`（`Bundles/` 下的构建缓存 json 除外，会自动重建）
- 命名空间统一是 `Ux`（asmdef `Unity.HotfixBase`，rootNamespace Ux），目录移动不影响编译

### 确定性审计结果：代码是照着确定性写的（重要信号）
扫描整个 `Manager/Combat/`，**零** Random / Time.deltaTime / Physics.* / DateTime.Now。
两个易踩坑都规避了：
- `CombatActionRunner.cs:76` HashSet<string> 用 `StringComparer.Ordinal`（避开 .NET 随机哈希种子），
  且只用于初始化去重校验，不在每帧逻辑
- `CombatActionRunner.cs:392-396 CompareAction` 全序排序（priority 相同再比 ActionId），

- 另：`CombatActionRunner.cs:114` 的 `foreach (_actions.Values)` 只是初始化校验（只抛异常），
  真正动作选择走已 Sort 的 `_startActions`，顺序安全

**但还差临门一脚**：16 处浮点（`CombatCommand.AimDirection` 是 Vector3、
`moveSpeedPerSecond`/`turnDegreesPerSecond` 是 float）。浮点跨 CPU 不一致
（x86 80位扩展精度 vs ARM NEON），帧同步必然发散。改造量可控（16 处）。
另：快照只覆盖状态机+当前动作，**不含位置与血量**（属性系统未实现）。

### 玩法适配度
| 玩法 | 模式 | 可行性 | 代价 |

## P0 落地：CombatMgr + BattleWorld

用户要求实现 P0，并问 BattleWorld 能否按项目规则命名成 Mgr。

### 命名结论：`CombatMgr` 是入口单例，`BattleWorld` 是被管理的实例（不是二选一）
项目惯例 `Manager/<模块>/<模块>Mgr.cs` = 模块级单例（`CombatMgr.Ins`）。
但世界**不能**是单例，三个硬理由：
1. 战报校验要在同进程跑第二份战斗；2. 主世界与回放世界须同时存在；
3. 快照回滚是世界级概念。
关系同 `ResMgr`→`ResHandle`、`ModuleMgr`→`ModuleBase`。
注意：Combat 模块因此有两个 Mgr（`CombatMgr` 运行时调度 + `CombatProfileMgr` 资源加载），
是项目首例，职责不重叠（如需合并可后续把 LoadAsset 挪进 CombatMgr）。

### 新增文件（`HotfixBase/Manager/Combat/`）
| 文件 | 职责 |
|---|---|
| `CombatMgr.cs`（模块根） | 单例，管理多世界 + 分发 SimulationClock 逻辑帧 |
| `Runtime/BattleWorld.cs` | 实体注册、8 阶段 tick、世界快照、状态 hash |
| `Runtime/ICombatEntity.cs` | 单位抽象，**不依赖 Unit/GameObject**（可无渲染跑） |
| `Runtime/BattlePhase.cs` | 阶段枚举 + `ICombatSystem` 插件接口 |
| `Runtime/BattleWorldSnapshot.cs` | 世界级快照（含 Position/Rotation） |

### 一帧八阶段（BattleWorld.TickFrame）
1 Commands → 2 Actions → 3 Timeline → 4 Hitbox → 5 Damage → 6 Buff → 7 Death → 8 Presentation
其中 1/2/8 是内置核心（调 ICombatEntity），3-7 目前只有插件位（`ICombatSystem`）。
**每阶段内插件先执行、内置核心后执行**。后续 P1-P4 只注册插件，不改核心循环。

### 驱动链变更（重要，后续排查看这里）
```
旧 SimulationClock → Scene.OnSimulationFrame → foreach players → Unit.TickSimulationFrame
新 SimulationClock → CombatMgr.OnFrameAdvanced → 各 BattleWorld.Tick(frame)
```
- 单位在 `CombatComponent.OnAwake/OnDestroy` 自行注册/注销主世界
- `Scene.OnDestroy` 调 `CombatMgr.Ins.DestroyAllWorlds()` 做场景级收口
- `Unit.TickSimulationFrame` 已删除；`Unit.SimulationFrame` 改为透传 `Combat.SimulationFrame`
- `CombatComponent.TickSimulationFrame` 保留为三阶段组合（单单位调试/测试用）

### 踩过的坑（复用价值高）
**生命周期顺序 bug**：`Scene.OnDestroy` 先 `DestroyAllWorlds()`，之后子组件的
`OnDestroy` 若走 `CombatMgr.Ins.Main` 会把主世界**重新创建**出来，
留下一个 Frame 停在旧场景的空世界 → 新场景时钟归零后所有 tick 被"回退忽略"。
修法：`CombatComponent.OnDestroy` 用 `CombatMgr.Ins.GetWorld(CombatMgr.MainWorldKey)?.Unregister(Id)`
（GetWorld 不自动创建）。

### 确定性设计
- 实体 `SortedDictionary<long, ICombatEntity>` 按 Id 升序；插件按 `(Order, 注册序号)` 全序
- `ComputeStateHash()` FNV-1a 64，覆盖状态机4层 + SimulationFrame + ActionId + ActionFrame
- **位置/朝向不进 hash**（未上定点数，浮点跨机不一致会变噪声）
- 逻辑帧只许正向推进，回退告警并忽略

### 测试
`Editor/Combat/Tests/BattleWorldTests.cs` 8 个用例（Id 升序遍历、同输入同 hash、
世界快照回滚、位置回滚、阶段顺序、同 Order 按注册序、非激活跳过、回退帧忽略、CombatMgr 增删）。
抽了 `CombatTestProfiles.cs` 共享 profile/action 构造，`CombatRuntimeTests` 改为委托调用。

### 遗留
远端玩家仍参与本地 tick，`TickMovement` 会与服务器下发位置打架（P0 前既有行为，未改动）。
修法：给 `ICombatEntity` 加"本地模拟/远端插值"标记，只改一处。

## CombatProfileName 来源（用户追问）

- `PlayerData.combatProfileName` (`Unit.cs:17`) 本地字段；唯一写入点 `SceneModule.EnterScene:33`

- 联网缺口：远端玩家无 `combatProfileName` 来源；需客户端按 `roleId` 映射或服务器下发
