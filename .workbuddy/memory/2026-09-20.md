## 架构讲解（无代码改动）

- **CombatController 的定位**：单个单位的纯逻辑总装，聚合 `States` / `Actions` / `Attributes` / `Buffs`。它是"那个固定顺序的执行者"——`Tick` 四步（`AdvanceTo` → `Actions.Tick` → 同步 Action 层 → Locomotion 三选一）次序不可换。只用 `UnityEngine` 的纯数据类型，不碰 MonoBehaviour / Transform。
- **它与 8 阶段的关系**：正交的两个轴。**只有阶段 2（Actions）走 `Controller.Tick` 这个统一入口**；阶段 3-7 全部绕过它直接改字段（Timeline 读 Actions / Hitbox 读 Actions+Life / Damage 写 target.Attributes+Buffs / Buff 读写 Buffs / Death 调 `SetLife`）。唯一借公开方法反向影响状态机的是 Death 阶段。
- **两种屏障同构**：阶段序管"单位之间"的依赖（所有单位推进完才求值），`Controller.Tick` 管"单位内部"的依赖（先推进动作，后判定位移）。Controller 是唯一同时持有这两套顺序定义的地方。
- **UnitStateMachine 与 CombatActionRunner 不是平行模块**，是"真数据 + 对外标签"：`StateLayer.Action` 只有 `Free/Executing`，是 `Actions.HasAction` 的镜像，在阶段 2 第 3 步刷新。

## 讲解：CombatComponent 为什么在上层 Hotfix 而不是 HotfixBase

结论不是习惯问题，是程序集依赖方向的硬约束。

- 三层单向：`Assembly-CSharp`（`Assets/Hotfix/`，无 asmdef）→ `Unity.HotfixBase` → `Unity.Main`。
- `CombatComponent` 依赖 `Unit`（`Hotfix/Modules/Scene/Unit.cs`）、`PathComponent`（`Hotfix/Common/AStar/`）、`Unit.Viewer` / `Animator` —— 全在上层。放进 HotfixBase 就等于让 HotfixBase 引用 Assembly-CSharp，而 asmdef 无法引用默认程序集 → 编译不过。
- 反过来它引用的 `CombatMgr` / `CombatProfileMgr` / `SimulationClock` / `CombatTimelinePlayer` / `ICombatEntity` 都在 HotfixBase，方向正好合法。
- `ICombatEntity` 是关键：接口在 HotfixBase、实现在 Hotfix，BattleWorld 只认接口 —— 这就是"纯逻辑能搬服务器"的机制来源。
- 佐证：`Hotfix/Common/` 下每个子目录都是一个 Component（AStar / FogOfWar / Playable / Camera / Operate / Combat），CombatComponent 与它们是同类。

## 讲解：CombatStateMachine.AdvanceTo 到底"推进"了什么

用户质疑：`AdvanceTo` 看起来只是 `SimulationFrame = targetFrame` + `StateLayerRuntime` 里 `Frame = Frame + delta`，注释却说"推进所有已存在状态的状态帧"，太夸大。

**结论：注释没说错，但"推进"这个词有歧义 —— 推进的不是逻辑，是表现层的播放头。**

链路（这是回答的关键）：

```
Controller.Tick 第 1 步  States.AdvanceTo(frame)
                          └─ 每层 StateLayerRuntime.Frame += delta（StateId == 0 则跳过）
                             ↓ 读到的地方全在表现侧
CombatTimelineResolver.Resolve
  :48  states.GetStateFrame(StateLayer.Life)        → 死亡表现的播放头
  :55  states.GetStateFrame(StateLayer.Control)     → 被控表现的播放头
  :69  states.GetStateFrame(StateLayer.Locomotion)  → Idle / Move 的播放头
                          ↓ 填进 CombatTimelineSelection.Frame
CombatTimelinePlayer.Evaluate
  :108  _component.EvaluateLayerFrame(TimelinePlaybackLayer.Base, plan.Base.Frame)
                          ↓ TimelineComponent.EvaluateLayerFrame
        timeline.EvaluatePlaybackFrame(frame)   ← 注释原文："按权威本地帧播放指定层"
```

- `StateId == 0` 的守卫 = 注释里"已存在状态"：四个状态枚举都从 **1** 开始（`CombatState.cs:17/24/30/38`），`0` 唯一表示"未初始化/已清空"，不存在"Idle 的 id 是 0 导致永不老化"的坑。
- **Action 层是例外**：`GetStateFrame(StateLayer.Action)` 生产代码零消费者，动作播放头走 `Actions.Current.ActionFrame`（`:66`）。该层照旧老化，只是没人读。测试里那三处 `Assert.AreEqual(0, …GetStateFrame(…))` 是唯一读者。
- **为什么用累加器而不是 `SimulationFrame - enterFrame`**：`ChangeState` 只写 `runtime.Set(stateId, 0)`（`:190`），**从来没存过 enterFrame**。改成派生式得再加一个字段，现在同样一个 int 就能表达，还少一个"两个数字可能互相矛盾"的不变量。`Advance(delta)` 而非 `Set(绝对帧)` 的另一个好处是状态机不知道绝对帧原点，`Initialize(frame)` 可从任意帧起算。
- **注释里"在本逻辑帧执行规则前"才是重点，它守的是一个顺序不变量**：`ChangeState` 会把该层 `Frame` 重置为 0，而 `AdvanceTo` 跑在同帧的 `SetLocomotion` / `SetAction` 之前 → **本帧刚进入的状态，本帧被 `Resolve` 读到 `Frame == 0`**，时间轴从第 0 帧采样。若把 `AdvanceTo` 挪到 `Tick` 末尾，新状态当帧就被老化成 1，开场少一帧姿态。同帧重复调用幂等（`targetFrame <= SimulationFrame` 直接 return）。
- 边界：`Frame` 是 `int`，`Advance` 里有 `Math.Min(int.MaxValue, …)` 饱和。主循环里 delta 恒为 1（`BattleWorld.Tick` 是 `while (Frame < frame) { Frame++; TickFrame(Frame); }`），所以数值上 `Frame == SimulationFrame - enterFrame`；`CombatComponent.TickSimulationFrame(frame)` 这种单机调试入口才可能给出 > 1 的 delta。
- **顺带发现两处零消费者扩展点**（与 `TryFind` / 取消窗口同类）：`CombatStateMachine.StateChanged` 事件全项目零订阅者；`IsPlaying(StateLayer, int)` 全项目零调用。

**插曲（重要）**：diff 里出现一处**不是本次改动**的变化 —— `TickLogic` 里的 `//已推进的帧` 变成了 `//当前的帧`。说明**用户在本轮对话进行中于 IDE 里编辑过这个文件**。脚本是"运行前重新读盘 → 全量回写"，那次编辑已被读到并原样保留。以后对这类用户可能同时在编辑的文件做全量回写，最好先提示一句，避免与 IDE 里未保存的版本相互覆盖。

## 讲解：StateChangeReason 是干嘛的

用户问这个枚举的用途。查证结论：**它是"标记型枚举"，只写入、不读出**。

- `ChangeState(layer, stateId, reason)`（`CombatStateMachine.cs:176`）收到 reason 后**完全不看它** —— 三个前置判断（`IsInitialized` / `CombatStateId.IsDefined` / `StateId == stateId`）都与 reason 无关，唯一用途是 `new StateChangedEvent(…)` 的第 4 个参数（`:191`）。所以 **reason 不影响任何行为**，纯粹是元数据。
- 它补的是 state id 说不出的信息：state id 只回答"变成了什么"，回答不了"**谁引起的**"（同一个 `Locomotion Idle → Move` 可能来自代码规则，也可能来自快照回滚）。
- 6 个值 ↔ 写入方：

| 值 | 谁写 |
|---|---|
| `Initialize` | `Initialize()` 连续设四层初始状态（`:46-49`） |
| `CodeRule` | `SetLocomotion` / `SetAction` 的**默认参数**（`:74` / `:79`）—— 即 `Controller.Tick` 第 4 步的 Locomotion 三选一 |
| `ActionStarted` / `ActionEnded` | `CombatController.cs:95` 显式传入（覆盖 `SetAction` 的默认值）；`CombatComponent` 与 `CombatController` 共 4 处 `ActionEnded` |
| `ExternalRequest` | `SetControl` / `SetLife` 的**默认参数**（`:84` / `:89`）；`CombatController.SetControl/SetLife` 又显式传了一次（`:133` / `:149`） |
| `SnapshotRestore` | `RestoreSnapshot()`（`:147`） |

- 两个易错细节：① **同状态重复 Set 时 reason 被整个丢弃** —— `ChangeState` 里 `StateId == stateId` 直接 `return false`，事件都不发，所以 `SetAction(Free, ActionEnded)` 在已是 Free 时静默无输出；② `RestoreSnapshot` **绕过 `ChangeState`**，自己直接 `Invoke`（`:143`），过滤条件是 `previous != value.StateId`，不走"同状态跳过"那条路。
- **文档注释与实现脱节**：`StateChangeReason.cs:3` 写"仅用于确定性调试、快照恢复和网络纠正"，但这三个消费者**一个都不存在**。理由同上一条 —— `StateChanged` 零订阅者，所以连 `SnapshotRestore` 也只是被写进去，没有任何人据此做区别处理。**和"零消费者扩展点"是同一件事的两面。**
- 同构对照：`CombatActionEndReason`（`CombatState.cs:48`，7 值）与它完全同类 —— `CombatActionRunner` 里 12 处写入，装进 `CombatActionChangedEvent.EndReason`（`:51`），该事件同样零订阅者。
- 位置观察：`StateChangeReason.cs` 是 `Asset/` 下**唯一单独成文件**的状态枚举，其余 6 个（`StateLayer` / `LocomotionState` / `ActionState` / `ControlState` / `LifeState` / `ActionMovementPolicy` / `CombatActionEndReason`）全挤在 `CombatState.cs` 一个文件里。`COMBAT_DESIGN.md:134` 的目录清单也是分开列的，属于既存组织方式。
- 结论：删不掉（6 个值都有写入方，`byte` 尺寸也不占空间），但今天也没有任何收益。将来真做确定性调试面板 / 网络纠正时它是现成的挂点 —— 前提是先给 `StateChanged` 找到订阅者。
