# 2026-09-15

## Combat 模块通读（idle / move / 普攻）

通读了 `Assets/HotfixBase/Manager/Combat`（纯逻辑）与 `Assets/Hotfix/Common/Combat/CombatComponent.cs`（Unit 桥接），梳理出的结构：

- **状态分层**：`StateLayer.Locomotion/Action/Control/Life` 四层，只有 Locomotion 有 Idle/Move/Airborne；Action 层只有 Free/Executing 二元，**具体技能不是状态节点**，由 `CombatActionRunner` 独立管理。
- **没有 Run 状态**。`PathComponent.IsRun` 是只写不读的死字段；走路/跑步只体现在 Profile 的 `state.0.1/0.2` Timeline 映射里。
- **Idle/Move 判定**：`CombatController.Tick:49-60`，优先级 Airborne > (IsMovementBlocked || 输入≈0 → Idle) > Move。输入阈值 sqrMagnitude <= 0.0001f。
- **移动输入链路**：InputSystem → `OperateComponent.OnMove`（相机空间转世界方向）→ `SceneModule.SendMove(Vector2)` → `UNIT_MOVE` 事件 → `Scene._OnUnitMove` → `PathComponent.SetPoints`。`SetPoints` 已改成把 `points[0]` 当**方向向量**，原 A* 路径跟随整段被注释。
- **普攻**：`OperateComponent.OnFire/OnKey` → `RequestAction(1001)` → `CombatCommandBuffer`（frame+1 入队）→ Commands 阶段取走 → `CombatActionRunner.Tick` 的 TryStart/TryCancel → 每帧 AdvanceTo 累加 ActionFrame，到 DurationFrames 结束。
- **表现**：`CombatTimelineResolver.Resolve` 产出 Base（Locomotion 状态 Timeline）+ Action（技能 Timeline）双层，`CombatTimelinePlayer` 同步到 `TimelinePlaybackLayer.Base(0)/Action(100)`；帧号来自状态帧 / ActionFrame，不是 Animator 自循环。

## 架构的流程视角（用过三张流程图讲）

数据流只有一条主线，分三层严格解耦：

1. **驱动**：`Scene.OnAwake` 启动 `SimulationClock.StartLocalRealtime(60)` → `CombatMgr` 订阅 `FrameAdvanced` → `BattleWorld.Tick(frame)` 用 `while (Frame < frame) TickFrame(++Frame)` 追赶（单帧上限 8 帧只告警不截断）。Unity Update 不参与战斗逻辑。
2. **一帧 8 阶段**：Commands → Actions → Timeline → Hitbox → Damage → Buff → Death → Presentation；每阶段先跑 `ICombatSystem` 插件（按 Order，同 Order 按注册序）再跑内置核心。实际只有 1/2/8 有内置实现。
3. **阶段 2 是全部实质逻辑**（`CombatComponent.TickLogic`）：① `Controller.Tick`（AdvanceTo → Actions.Tick 的 Start/Cancel → 刷 Action 状态 → 判 Locomotion）② Resolve 表现计划 ③ Synchronize 切轨道 ④ TickMovement 位移。**先推进动作再判 Locomotion** 的顺序是"攻击锁移动"能自动生效的原因。
4. **输入与逻辑通过"帧号 + 命令缓冲"解耦**：按键写进 `当前帧+1` 的队列，下一帧才被取走，延迟 1 帧（16.7ms）。这是网络同步 / 录像能复用同一套逻辑代码的前提。
5. **对象构成**：`Unit` 挂 Timeline / Path / Combat / Operate 四组件；`CombatComponent` 实现 `ICombatEntity` 并持有 `CombatController`，后者 = `UnitStateMachine`（四层状态+状态帧）× `CombatActionRunner`（动作表+动作帧）。
6. **代码 / 资源边界**：状态定义与转换规则、时序阶段顺序、确定性要求 → 代码；时长、取消/命中窗口区间与半径、Timeline、移速 → Profile 资源。

## 「移动输入算不算命令」——架构上的定性（用户提问）

结论：**不算**。两者的判据是"离散事件 vs 当前值"：

| | `MoveInput` | `CombatCommand` |
|---|---|---|
| 类型 | `Vector2` | 结构体（RequestId/SimulationFrame/ActionId/TargetId/AimDirection）|
| 存储 | `PathComponent.MoveVector2`，**单个可覆盖字段** | `CombatCommandBuffer`，按帧号分桶字典 |
| 写入 | 覆盖，不留痕 | 追加，累积到被消费 |
| 一帧条数 | 概念上恒为 1 | 可多条，故有 Count 与排序 |
| 生命周期 | 活到下次写入 | Consume 一次即消失 |
| 帧号 | 无 | 有，且是主键 |

两者在**同一处汇合**：`CombatController.Tick(frame, moveInput, commands)` 的三个参数。差别不在 TickLogic 里，而在"到达它之前存在哪里"。

**由此暴露的关键事实（重要，后续接网络/帧同步会撞上）**：
- 位移的同步方式是 `EventType.UNIT_UPDATE_POSITION`（`Scene._OnUnitUpdatePosition` 直接把广播来的坐标写进 `player.Position`）→ **移动走状态同步**，技能走"帧号命令重放"。
- **移动输入没有任何可重放通道**：`SendMove` 只有两个调用方（`OperateComponent.OnFire/OnMove` 本地输入、`SeekerComponent.OnPathComplete` 的 A* 寻路），没有录制/回放入口；`BattleWorld.ComputeStateHash` 也不含位置与朝向（P0 未引入定点数）。
- `CombatComponent.EnqueueCommand`（网络/录像命令入口）目前**零调用方** —— 命令通道是"预留已就绪但未接线"，移动连通道都没有。
- 潜在风险：`CaptureSnapshot/RestoreSnapshot` 会恢复 Position/Rotation，但回滚后重算所用方向仍取当前 Unity 摇杆值 —— 真接帧同步时会出现"回滚重算结果和当初不一致"。

已把这两点写进代码注释：`CombatComponent.MoveInput`（说明它不是命令、及同步方式差异）、`CombatController.Tick`（说明两参数性质不同、只有 commands 需要队列与帧号）。
