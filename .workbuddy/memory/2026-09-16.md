## BattlePhase 新增阶段的改动清单（用户提问）

问题：以后新增 `BattlePhase` 类型，是不是都要在 `BattleWorld.TickFrame` 里加一行 `RunSystems`？

**分两种情况，答案不同：**

| 目的 | 要不要动 TickFrame |
|---|---|
| 给**已有空阶段**（Timeline / Hitbox / Damage / Buff / Death）接实现 | **不用**。对应 `RunSystems` 早已写好，只是桶是空的 —— 写一个 `ICombatSystem`（`Phase = 目标阶段`）再 `world.AddSystem` 注册即可。这正是插件设计的目的 |
| **新增一个阶段类别**（如 Dodge / Resource / AI） | **要**，且必须插在正确的行间 |

新增阶段要同步**三处硬编码**，漏改不会编译报错、只会静默失效：

1. `BattlePhase.cs` 枚举加成员（`enum : byte`，值被当 `_systemBuckets` 数组下标用，必须 0..N-1 连续）
2. `BattleWorld.PhaseCount`（改小 → 新阶段插件被 `phase >= PhaseCount` 拦下，每帧刷"战斗子系统阶段越界"日志）
3. `_systemBuckets` 初始化列表里 `new()` 的个数（改小 → `EnsureSystems` 里数组越界）
4. 外加 `TickFrame` 里插 `RunSystems`

**最大的坑：执行顺序 = `TickFrame` 里 `RunSystems` 的书写顺序，与枚举值顺序无关**（枚举只做数组下标）。
- 只调枚举顺序 → 行为完全不变（极易误以为改过了）
- 调 `RunSystems` 调用顺序 → 行为全变
两处可以静默不一致。

原因：阶段 1/2/8 夹着内置实体循环，阶段 3-7 是纯插件，所以没法用 `for (phase...) RunSystems(phase)` 统一展开，顺序只能手写。

以上规则已写进代码注释：`BattleWorld.PhaseCount` 上方、`TickFrame` 开头。

## Timeline 编辑器的「命中 clip」会不会注册到 Hitbox 插件？（用户提问）

**结论：不会。** 两者之间没有任何连线的代码，数据链在运行时是断的。

证据链（三层）：

1. **编辑器层**：Timeline 里新增的"命中" clip 真身是 `CombatHitWindowEditorClip`，创建走 `CombatLogicTimelineSource.AddHitWindow()`（`Editor/Combat/Timeline/CombatLogicTimelineSource.cs:301-328`）——用 `SerializedObject` 往 `action.hitWindows` 数组插一项（`stableId`/`StartFrame`/`EndFrame`），`Save()` → `AssetDatabase.SaveAssets()` 就结束了。
   - 关键：`GetTrackTypes()` 返回**空数组**（`:75-79`），两条轨（取消窗口 / 命中窗口）在构造函数里写死，`RebuildAdapters()` 每次从 `action.HitWindows` 重建 clip 列表 → **这两条轨是"资产的反读投影"，不是插件注册机制**。加 clip 等价于给数组加一项。
2. **阶段层**：`BattlePhase.Hitbox` 全项目只有两处引用 —— `BattleWorld.cs:404` 的 `RunSystems(BattlePhase.Hitbox, frame)` 与 `BattleWorldTests.cs`。运行时 `world.AddSystem` 零调用方。
3. **运行时读链**：`CombatActionAsset.hitWindows` ← `CombatActionRunner.AppendActiveHitWindows()`（`:323`，按 ActionFrame 过滤）← `CombatHitResolver.AppendResolvedHits()`（`CombatHitResolution.cs:111`）← **无人调用**（调用方只有 `CombatRuntimeTests.cs`）。数据可读，但没人读。

→ 命中窗口目前只是"资产里两行数字 + 编辑器里一个方块"，**缺执行者**。设计意图（`BattlePhase.cs` 注释）本来就是"clip 只提供数据，结算由 BattleWorld 统一调度"，所以方向没错，只是 `HitboxSystem` 还没写。

**另一个坑：世界坐标 → 毫米的换算全项目不存在。** `CombatFixedPoint` 声明为整数毫米，`CombatHitResolver` 注释要求"坐标由上层从本帧逻辑状态提供，不读 Transform"，但没有任何 `ToMillimeters` 之类的换算代码（grep 只有 `CombatFixedPoint` 自身与 `TimerHelper` 的日期格式）。测试里直接构造 `CombatFixedPoint(0,0)` / `(1,0)`，完全没碰 Unity 的 float 坐标。
→ 写 HitboxSystem 时必须先定"原点 + 1 世界单位 = 多少毫米"的约定；**定了这个约定之后，才能判断 `radiusMillimeters: 14` 到底是对是错**（之前只是"疑似漏换算"，现在可以说：该值对错取决于尚未定义的换算比例）。

## 命中 clip「运行时怎么走到 Hitbox 插件」的完整链路（用户提问）

**结论：走不到，链在"每帧的调用者"这一跳断掉。** clip 只是数据，不是注册机制。

已打通（数据 + 能力）：
1. 编辑期 clip → `action.hitWindows`（`AddHitWindow`，`AssetDatabase.SaveAssets`）
2. 加载期 → `CombatActionRunner._actions[actionId]` 持有 `CombatActionAsset`
3. 阶段 2 → `Start` / `AdvanceTo` 让 `Current.ActionFrame` 逐帧累加
4. `CombatActionRunner.AppendActiveHitWindows(List<CombatActiveHitWindow>)`:323 —— 用 `Current.ActionFrame` 对 `CurrentAsset.HitWindows` 做 `[StartFrame,EndFrame)` 过滤。**无副作用、不分配内部集合**
5. `CombatHitResolver.AppendResolvedHits(runner, source, targets, output)`:111 —— 只做几何判定

缺失：
- 没有任何 `ICombatSystem(Phase = Hitbox)`；`world.AddSystem` 运行时零调用方
- 无坐标换算（`ICombatEntity.Position` 是 Unity `Vector3` float 米，`CombatFixedPoint` 要整数毫米）
- 无伤害/Buff/死亡插件（阶段 5-7）

**插件能拿到的入口（重要，可复用）**：
- `world.Entities`（`BattleWorld.cs:60`，类型是 `IReadOnlyCollection<ICombatEntity>`）
- `entity.Controller.Actions` → 即 `CombatActionRunner`（`CombatController.cs:24` 是 public get 属性）
- `entity.Id` / `entity.Position`(Vector3) / `entity.Rotation`
- `entity.Controller.States.Life`（可用来排除死亡目标）

**三个必须先处理的现实问题**：
1. **`Id` 必须 > 0**：`AppendResolvedHits` 对 `source.EntityId <= 0` 或任一 `target.EntityId <= 0` 直接 throw。`CombatComponent.Id => Unit?.ID ?? 0`；`Unit.ID` 来自 `IDGenerater.GenerateId()` = `Interlocked.Increment`（`Main/Common/IDGenerater.cs:11`）→ 从 1 递增，是正数。但 `ICombatEntity.Id` 注释要求"不能用每次运行都会变的值"，全局自增计数器的值恰取决于创建顺序 → 接帧同步时是隐患。
2. **坐标约定未定义**：必须先定"原点 + 1 世界单位 = 多少毫米"，否则 `radiusMillimeters: 14` 无法判断对错。
3. **目标筛选缺失**：resolver 不做敌我/存活筛选，`targets` 要由插件筛好再传入（重复 Id 会 throw）。

**反直觉但有用**：`TryAcceptHit` 写入的 `_acceptedHits` **参与 `ComputeStateHash`**（`BattleWorld.cs:316-324`）。所以只要 HitboxSystem 跑起来，即使伤害结算还没写，**状态哈希也会立刻变化** → 可当作"插件真的被调用、窗口真的命中"的免费验证手段。

**GC 注意**：`world.Entities` 静态类型是接口 `IReadOnlyCollection<ICombatEntity>`，直接 `foreach` 会装箱 `SortedDictionary` 的结构体枚举器 → **每帧一次堆分配**。`TickFrame` 内部因此用 `_ordered` 数组缓存 + 索引循环。

**字段消费分界（这是"插件里找不到帧号"的原因）**：

| 字段 | 谁消费 | 插件可见 |
|---|---|---|
| `StartFrame` / `EndFrame` | Runner 的 `IsActive` 过滤，内部消耗 | ❌ |

## 「HitboxSystem 在哪关联了 ActionHitWindow」的精确答案（用户追问）

**关联动作只有一行**：`HitboxSystem.cs:92` 把 `entity.Controller.Actions`（`CombatController.cs:24` 的 `CombatActionRunner`）当参数传给 `CombatHitResolver.AppendResolvedHits`。**没有注册、没有回调、没有按 ActionId 查表。**

硬证据：`grep -n "ActionHitWindow" HitboxSystem.cs` → **空**。插件里压根不出现这个类型名。

5 跳读取链：
1. `HitboxSystem.cs:92-96` 传 runner 进去
2. `CombatHitResolution.cs:157` `runner.AppendActiveHitWindows(windows)` —— resolver 转手问 runner
3. `CombatActionRunner.cs:335-341` `CurrentAsset.HitWindows[i]` + `window.IsActive(Current.ActionFrame)` ← **ActionHitWindow 只在这里被读到，从未离开 runner**
4. `CombatActionAsset.cs:64-67` `actionFrame >= StartFrame && actionFrame < EndFrame`
5. `CombatActionRunner.cs:342-347` 打包成 `CombatActiveHitWindow` —— **值拷贝**（Start/End/Shape/Radius 都是拷出来的副本）
6. `CombatHitResolution.cs:173-185` 用拷贝出的 Shape/Radius 做 `IsInsideCircle` + `TryAcceptHit` 去重

绑定"哪份窗口表"的点是 `CombatActionRunner.cs:653` `CurrentAsset = action`（`Start()` 内；`:475` 是 Confirm 路径），此时 `CurrentAsset × Current.ActionFrame` 配成一对。

→ 一句话：**插件不持有配置，只是每帧拿着 runner 去问一次；ActionHitWindow 的存在感止于第 3 跳。**

## 阶段 4/5 之间没有数据通道（用户确认流程时暴露的缺口）

用户的理解："收集活目标 → AppendResolvedHits 判命中 → 扔进待结算列表 → 等结算阶段触发"。**前两步对，后两步错。**

| `BattleWorld` 上一个每帧清的 `List<CombatHitCandidate>` | 新建 | 最简单；顺序天然确定（阶段 4 按 Id 升序填）。但 `CaptureSnapshot`（`BattleWorld.cs:196-229`）只存 Combat + Position + Rotation，回滚后需能重建 |

## 插件实例的粒度规则（用户问"要不要注册多个"）

**结论：一个世界一个实例，一个就够；有几个世界就要几个；绝不可跨世界共享。**

- **不按单位注册**：`HitboxSystem.Tick(world, frame)` 自己遍历 `world.Entities`，内部没有"我是哪个单位"的概念。一个实例服务整个世界。
- **`_systems` 是 `BattleWorld` 的成员**（非全局单例）→ 主世界 + 每个战报回放世界各需一个。`CombatMgr.CreateWorld` 里每个世界 `new HitboxSystem()`（`CombatMgr.cs:98`），正确。
- **禁止共享实例**：`HitboxSystem` 持有 4 个可变复用缓冲 `_entities`/`_targets`/`_windows`/`_hits`（`:53-56`）。跨世界共享 → 后者的 `Clear()` 吃掉前者刚收集的中间结果。`CombatMgr.OnFrameAdvanced` 顺序 tick 各世界（`CombatMgr.cs:139`），阶段 4 填完阶段 5 马上读，顺序上可能侥幸不炸，但属运气而非设计。
- **`AddSystem` 去重是 `ReferenceEquals`**（`BattleWorld.cs:484-494`）：同一实例重复注册 → no-op（安全）；**两个不同实例都会注册成功** → 每帧跑两遍。不会双倍伤害（`TryAcceptHit` 按 actionInstanceId+windowId+targetId 挡住），但双倍几何计算 + 双倍日志。
- 只有"同一世界里跑两套不同筛选规则"时才需要多个实例（用 `Order` 区分次序）。当前不需要。
- 注意：`Editor/Combat/Tests/*` 直接 `new BattleWorld(...)` 绕过 `CombatMgr`，**测试世界不带任何默认插件**（有意为之）。

## 为什么只有阶段 1/2/8 的 RunSystems 后面带实体循环（用户提问）

**判据：这一阶段有没有"框架级、必须对所有单位做"的事。**

理由在 `ICombatEntity.cs` —— 它只向世界暴露**三个**逐帧方法，正好一一对应：
- `ConsumeCommands(long frame)`（`:31`）→ 阶段 1
- `TickLogic(long frame, in CombatFrameCommands)`（`:34`）→ 阶段 2
- `TickPresentation(long frame)`（`:37`）→ 阶段 8

这三个是"世界↔单位的契约"，属框架职责 → 必须内置在世界里，所以有实体循环。
其余阶段（Timeline / Hitbox / Damage / Buff / Death）**没有任何内置逐单位操作**，BattleWorld 只做一次 `RunSystems` 就走 → 要遍历单位就由插件自己在 `Tick(world, frame)` 里用 `world.Entities`（HitboxSystem 正是如此）。

**连带约束**：阶段 1 与阶段 2 的循环必须共用同一套索引 —— `_frameCommands[i]` 与 `_ordered[i]` 一一对齐，所以 `EnsureOrder` 里两个数组一起扩容（`BattleWorld.cs:437-438`）。改循环时不能只改一处。

→ 已把上述理由补进 `BattleWorld.TickFrame` 的文档注释（仍是纯注释，去注释后代码与 HEAD 一致）。

## `_ordered` 到底是什么（用户提问）

**是 `_entities` 值序列的扁平化缓存，"排序"这个动作并不存在。**

- `_entities` 是 `SortedDictionary<long, ICombatEntity>`（`BattleWorld.cs:25`）—— **自身就是按 Id 升序的**，注释 `:24` 已写明。

## 频繁实体注册/注销会不会导致 `_ordered` / `_frameCommands` 反复重分配（用户提问）

**结论：会，但触发条件比想象的窄，且量级很小，不是热点。**

触发条件（`BattleWorld.EnsureOrder`）：
- 只有 `_entityOrderDirty` 为 true 才继续 → 该标志**仅由 `Register`（`:82`）/`Unregister`（`:95`）/`Clear`（`:118`）置位**；`EnsureOrder` 在 `Tick`（`:188`）/`CaptureSnapshot`（`:199`）/`RestoreSnapshot`（`:239`）/`ComputeStateHash`（`:288`）前调用，非脏则立即返回 → **无进出事件时零开销**。
- 重分配条件 = **脏 且 `_ordered.Length != count`**：
  - 同一批内"进一个 + 出一个"（净数量不变）→ **不重分配**，只原地重填；
  - 数量在同一个值上下**反复摆动**（九宫格玩家跨格子边界的典型形态）→ 每次 `EnsureOrder` 都重分配一次 ← 这才是用户担心的真实场景。

量级：`ICombatEntity[]` 8 B/元素 + `CombatFrameCommands[]` 8 B/元素（该 struct 只含一个 `IReadOnlyList<CombatCommand> _items` 引用，`CombatCommand.cs:66-71`）→ **合计 16 B/实体**。50 单位 ≈ 800 B/次，200 单位 ≈ 3.2 KB/次。LOH 阈值 85 KB ≈ 5300 单位，**九宫格规模不可能碰到**。
更值得关注的是 `SortedDictionary` 增删本身的结点分配 + O(log n)，那是**每个实体都要付**的，与数组重分配无关。

**可选优化（grow-only 容量数组）**：数组只扩容不缩容 + 单独 `int _entityCount` 字段。改动 5 处：`CaptureSnapshot:201-202`、`RestoreSnapshot:241`、`ComputeStateHash:290`、`TickFrame:333`、`EnsureOrder:409-411` 里的 `_ordered.Length` 全部换成 `_entityCount`。好处是消除数量摆动时的反复分配；代价是数组永不缩容、保留高水位内存（16 KB/1024 槽，可接受）。
注意：**不能**简单把 `_frameCommands` 换成 `List<T>` —— 阶段 2 用 `in _frameCommands[i]` 传参，`List<T>` 的索引器对 struct 返回副本，拿不到 `in` 引用。

→ 已把"精确长度数组 + 摆动即重分配 + 可选容量数组方案"写进 `BattleWorld.EnsureOrder` 注释（纯注释，`git diff` 剥离注释后仅剩用户自行添加的构造函数注册那一行）。

## 阶段 1 为何"插件在前、抽干在后"＋能否把遍历抽成插件（用户提问）

**为什么这个顺序有意义（不是随手写的）**：
- `CombatCommandBuffer.Enqueue`（`CombatCommand.cs:137-145`）**不校验帧号** → 当前帧也能入桶；
- 抽干（`ConsumeCommands` → `Consume`，`:147-155`）会 `_frames.Remove` 整桶。
- ⇒ 只有在抽干**之前**运行的插件，才能把"本帧命令"塞进去并被**本帧**消费。这正是网络/录像权威命令注入需要的时机（入口 `CombatComponent.EnqueueCommand`，`:159`，目前零调用方）。
- 阶段 2 同理：Actions 阶段插件改的状态（buff/移速）能被**同一帧**的核心 `TickLogic` 用到，不需要延迟一帧。
- 统一模板"插件→核心"覆盖 1/2/8 三处，不是为阶段 1 单独设计。

**隐蔽坑**：`BattleWorld` **没有暴露 `_frameCommands`**（私有字段 `:34`，无访问器）。Commands 阶段插件只有两条路：往队列 Enqueue（正常），或自己调 `entity.ConsumeCommands(frame)` → **把命令从核心手里抢走**，抽干循环随后只拿到 `Empty`。能编译能跑、无声失效。目前无 Commands 阶段插件（只有测试里的 `RecordingSystem`）。

**能否把遍历抽成插件：技术上能，但不该。** 障碍：
1. `_frameCommands` 私有且**下标与 `_ordered` 绑定** → 必须暴露 `SetFrameCommands(entity, cmds)` 之类，把内部布局泄给插件 API；
2. **框架不变式会依赖插件注册**：插件没注册 → 命令永不抽干 → 阶段 2 全是 `Empty` → 技能永远起不了手；
3. **顺序脆弱**：抽干必须晚于所有其他 Commands 插件，但插件排序是 `Order` 升序 + 注册先后（`CompareSystem`）→ 事后加一个 Order 更小的 Commands 插件就静默改变语义；
4. **性能倒退**：核心循环是 3 行数组索引；插件版走 `foreach (world.Entities)` 要付枚举器装箱（每帧一次堆分配）+ 每实体接口分派。
→ 结论：遍历属"世界↔单位契约"（`ICombatEntity` 三方法），framework 职责；可定制的是**策略**（塞什么命令、怎么处理），不是遍历本身。

**若诉求是"Commands 阶段只读观察命令"**：当前只有破坏性的 `Consume`，缺只读 `Peek`。补 `Peek(frame)` 时注意 `new CombatFrameCommands(list)` 构造函数会**复制并排序** List（`:81-83`）→ 每次分配，只宜诊断用，别进热路径。

→ 已把上述"阶段 1 顺序的真实理由 + 抢命令的坑"写进 `BattleWorld.TickFrame` 阶段 1 注释（纯注释）。

## Commands 阶段插件到底什么时候需要（用户提问）+ 对上一轮结论的纠正

用户问：`RunSystems(BattlePhase.Commands, frame)` 干嘛？什么情况注册这个插件？手动执行是不是不需要？

**这一步本身**：`RunSystems`（`BattleWorld.cs:379-386`）就是遍历 `_systemBuckets[(int)phase]` 逐个 `Tick(this, frame)`。**桶空 = for 0 次 = 这行等于没写**。当前 Commands 桶是空的（唯一 Commands 插件是测试里的 `RecordingSystem`）。

**它和后面实体循环是两件事**：RunSystems = 外部输入注入机会（策略）；实体循环 = 框架收命令（契约，对应 `ICombatEntity.ConsumeCommands`）。

**两个命令入口的差别（判据）**：
- `CombatComponent.RequestAction`（`:144-157`）帧号**写死** `SimulationClock.Ins.CurrentFrame + 1` → 只能表达"我现在按了 Q"
- `CombatComponent.EnqueueCommand`（`:159-163`）帧号**由调用方给** → 才能表达"帧 43 执行这个"

**❌ 纠正上一轮**：我上一轮说"录像回放必须注册 Commands 插件"——**说过头了**。因为 `CombatCommandBuffer.Enqueue`（`:137-145`）**不校验帧号**，未来帧也能先存进桶。所以：

| 回放做法 | 需要插件吗 | 适用 |
|---|---|---|
| **全量预载** | ❌ 不用 | 录像已完整拿在手上（文件/内存）。回放前遍历一遍，把每条命令 `Enqueue` 到对应单位，未来帧会先存着，等世界推到那帧自然消费 |
| **按帧投递** | ✅ 需要 | 数据**流式**到达（边下载边播、逐帧收包），每帧问一次"这帧到了吗" |

→ **真正的判据是"命令数据是不是边来边有"，不是"是不是录像"**。

**那 Commands 插件还有必须用途吗**：几乎没有。全量预载覆盖绝大多数录像场景；网络包到达是异步事件，收到直接 `EnqueueCommand` 即可（帧号服务器给了）。它主要是**为架构对称性保留的位置**。

**但走插件路线现在有个硬障碍**：`ICombatEntity`（`ICombatEntity.cs:16-37`）**只有 `ConsumeCommands`，没有 `EnqueueCommand`**（实现在 `CombatComponent.cs:159`，Unit 侧）。所以：
- **Unity 侧回放**（能拿到 `Unit` → `Unit.Combat.EnqueueCommand`）：✅ 可行，不改接口
- **纯逻辑侧回放**（插件只能从 `world.Entities` 拿 `ICombatEntity`）：❌ 塞不进去，必须先给 `ICombatEntity` 补 `void EnqueueCommand(in CombatCommand command)`

**另一个录像格式前提**：`CombatCommand` 结构里**没有 entityId 字段**（命令存在"哪个单位的队列里"这一事实本身就是归属）。所以录像必须额外记"这条命令属于哪个单位"，插件才能找到对应 `ICombatEntity`。

**插件纪律（再次强调）**：Commands 插件只准"塞"，不准自己调 `ConsumeCommands` —— 会把命令从核心循环手里抢走，后续抽干只拿到 `Empty`。

## 插件能力边界的精确版（用户要求"只讲机制、不讲业务"）

## 用户尝试把 TickFrame 的 8 段手写改成枚举循环 —— 评估结论

用户提议：
```csharp
var count = _ordered.Length;
foreach (BattlePhase phase in Enum.GetValues(typeof(BattlePhase)))
{
    RunSystems(phase, frame);
    if (_phaseActions.TryGetValue(phase, out var action)) action(count, frame);
}
```

**方向对的点**：执行顺序变成**单一来源**（枚举值顺序），消除了"枚举顺序 vs TickFrame 书写顺序"可静默不一致的坑；新增阶段少改一处。

**三个问题（按严重度）**：

1. **可能直接抛 `InvalidCastException`（`Enum.GetValues` 返回类型陷阱）**
   `BattlePhase` 是 `enum : byte`。`Enum.GetValues(Type)` 在部分 .NET/Mono 实现下返回**底层类型数组**（`byte[]` 而非 `BattlePhase[]`），此时 `foreach (BattlePhase phase in ...)` 会对装箱的 `byte` 做拆箱转型 → 抛异常。而 `(BattlePhase[])Enum.GetValues(...)` 强转同样会失败。
   **安全写法**：逐元素转换 `result[i] = (BattlePhase)values.GetValue(i);`（`GetValue` 返回 object，转换不依赖数组运行时类型）。Unity 2021.3 走 Mono + .NET Standard 2.1（**无** `Enum.GetValues<T>()` 泛型版，那是 .NET 5+），此处必须实测。

2. **每帧堆分配（性能倒退）**
   `Enum.GetValues` 每次调用 `new` 一个数组；返回类型是 `Array` → foreach 走**非泛型 `IEnumerator`** 路径 → 再分配一个枚举器，且每次迭代拆箱。60Hz 下每秒约 60 次分配。这与该框架"稳态零分配"的设计直接冲突 —— **`_ordered` 数组存在的唯一理由就是避免 foreach 把 `SortedDictionary` 枚举器装箱**。
   **修法**：`private static readonly BattlePhase[] PhaseOrder`（静态缓存一次）+ 索引 `for` 循环。

3. **框架不变式从"代码结构"退化为"字典内容"（设计风险）**
   现在"命令必须被收"靠写死的 for 循环保证；改成 `_phaseActions` 字典后，**漏配 Commands → 命令永不抽干 → 阶段 2 全 `Empty` → 技能永远起不了手**，且能编译、能跑、不报错。
   **缓解**：字典只在构造函数里填死（外部不可改）+ 启动期断言。

**推荐的更优版本（switch，而非字典）**：保留"内置核心是显式代码、不可缺省"这个属性，同时顺序单一来源、零分配：
```csharp
private static readonly BattlePhase[] PhaseOrder = BuildPhaseOrder();
// BuildPhaseOrder(): 逐元素 (BattlePhase)values.GetValue(i) 转换

private void TickFrame(long frame)
{
    var count = _ordered.Length;
    for (var i = 0; i < PhaseOrder.Length; i++)
    {
        var phase = PhaseOrder[i];
        RunSystems(phase, frame);
        switch (phase)
        {
            case BattlePhase.Commands:     SampleCommands(count, frame);     break;
            case BattlePhase.Actions:      AdvanceUnits(count, frame);       break;
            case BattlePhase.Presentation: AdvancePresentation(count, frame); break;
        }
    }
}
```
（`byte` 枚举的 switch 会编译成跳转表，8 次/帧可忽略。）

**语义变化须知**：改前"改枚举值顺序不影响行为"（TickFrame 写死顺序）；改后"枚举值顺序 = 执行顺序"。要把这条新语义写进 `BattlePhase` 注释，并保持值 0..N-1 连续无重复。

## 21:5x 收敛每帧全场遍历 + 干掉 foreach 装箱分配

**起点**：用户问「HitboxSystem 每帧都遍历 world.Entities，但大部分帧实际没命中，能不能把逻辑挪到 `_hits.Clear();` 前」。

**回答**：方向对，但**字面位置不对** —— `_hits.Clear()` 在 events 循环**内部**（每个攻击者前一次），不是帧开头；照字面挪会把目标收集塞进循环体 → N 个攻击者 × O(N) 次全场遍历，比改前更差。正确形态是**延迟收集 + 只收一次**，用**局部** `targetsReady` 标志（局部量不需要跨帧复位，没有漏复位这种失败模式）。

**改动**：
- `BattleWorld.cs`：新增 `IReadOnlyList<ICombatEntity> OrderedEntities => _ordered;` —— 给逐帧遍历用，避免 `Entities`（静态类型是接口）foreach 时装箱 `SortedDictionary` 结构化枚举器。文档写明「与内置阶段同一份快照，中途注册的单位下一帧才可见」。
- `HitboxSystem.cs`：目标收集抽成 `CollectTargets(world)`，在 events 循环里首次遇到 `HasHitWindows` 时才调；遍历换成 `OrderedEntities` 索引。新增注释写清「为什么延迟收集仍安全」的**前提**：阶段 4 内没有任何东西改生命/位置（位置在阶段 2 定稿，PendingHits 到阶段 5 才消费），所以收集时刻不影响结果；**谁以后在命中阶段里改位置（击退），这条前提就破了，必须挪回 Tick 开头无条件执行**。
- `CombatTimelineSystem.cs` / `CombatBuffSystem.cs` / `CombatDeathSystem.cs`：同样把 `foreach (world.Entities)` 换成 `OrderedEntities` 索引遍历（这三处是每帧必遍历的，装箱分配省不掉遍历但能省掉分配）。BuffSystem 的类注释也同步改掉「按 world.Entities 的 Id 升序」这句。

**行为差异（可接受且更一致）**：改用 `_ordered` 后，Tick 中途注册的单位在阶段 3/4/6/7 看不到 —— 与内置阶段（PhaseCommands/PhaseActions 一直用 `_ordered`）一致；旧写法下中途注册的单位能在阶段 4 被当成目标，但它在阶段 1/2 又没跑过逻辑，本身就是不一致。

**成本清点（每逻辑帧，时钟卡顿最多补 8 帧）**：
| 位置 | 改前 | 改后 |
|---|---|---|
| Timeline 遍历 | O(N) + 1 盒 | O(N)（不可避免，要扫出谁在出招） |
| Hitbox 遍历 | O(N) + 1 盒 + N 次 ToFixedPoint | **无窗口时整段跳过**，0 |
| Buff/Death 遍历 | 各 1 盒 | 0 盒 |
| `AppendResolvedHits` 全参重载 | `new List<int>` + `new HashSet<long>`，**每个攻击者 2 次** | 未改（待定） |

**遗留可优化点**：`CombatHitResolution.cs:149-150` 的 `new List<int>(targets.Count)` + `new HashSet<long>()` 是现在最大的每帧分配源，且只在「真有命中窗口」那一帧发生。要消除需要给解析器传复用 scratch（改 5 参重载签名或加一个 scratch 类型），**未做，等用户定**。
